Interview revision sheet. Every demo on this page is live — click it and watch the console pane at the bottom. Values marked ✅ were verified under jsdom 29; ❓ marks the one claim that needs a real browser, which is now you.

THE MODEL 🧠

A click doesn't "happen on the button". The browser builds the path from window down to the target, then walks back up:

window → document → html → body → … → TARGET → … → body → document → window
\________________ capture phase _____/  \______ bubble phase ______/

addEventListener listens on the bubble phase unless you pass capture. A listener on a parent therefore sees every click from its subtree — that's delegation, and it's why rows added later still work: nothing was ever bound to the row.

💡 The one-liner: delegation works because the event comes to the parent anyway. One listener on a stable ancestor, plus e.target.closest(selector) to find what was hit.

Your original note: A button click doesn't fire it on the button, event flows from window to the target (capture phase) and reaches the target and comes back up (bubble phase). addEventListener listens on the bubble phase by default. event delegation: put one event listener on the parent and it captures every child events.

    4. Listener options 🎛️

    { once: true } and { passive: true }

    passive link (opens a tab) non-passive link (cancelled)

    ✅ once runs the handler exactly one time however many times you click. ⚠️ passive: true makes preventDefault() a no-op: defaultPrevented stays false and the browser navigates anyway (Chrome also logs "Unable to preventDefault inside passive event listener invocation"). The second link is identical minus passive, and it is cancelled. passive is a promise you make to the browser so it can scroll without waiting for you — use it for scroll/touch/wheel, never with preventDefault.

    { signal } — drop many listeners at once

    fired: 0

    ✅ Fires until Abort, then never again (verified: 1 call, then 0). ⚠️ removeEventListener needs the identical function reference and a matching capture flag — an inline arrow can never be removed. That's why signal is the modern answer, and it's the same primitive as fetch cancellation.

    5. Gotchas ⚠️

    5.1 HTML comments do not nest — the bug that was in this file

    The first end marker wins: an inner one closes the outer comment. A block here opened with the todo-list markup and was closed by the end marker of an "Exercise" comment two lines down, so everything after it went live — four rows, the Abort button, a link, and a stray end marker printed as page text. The rows also lost their list wrapper and were parented to BODY, so the #items-list listener never saw them: clicking Delete logged nothing, which looks exactly like "delegation is broken". ✅ Verified with a spec-compliant parser — and hit again while writing the note about it, because quoting the marker inside a comment closes that comment too.

    ✅ Fix: one wrapper, no inner end marker. To park markup tidily use a <template> element or <script type="text/plain"> instead of commenting it out. (This sheet sidesteps the whole problem: the notes are page content now, not comments.)

    5.2 preventDefault vs stopPropagation vs stopImmediatePropagation

    Your note: 1. preventDefault - to prevent browser's default action. 2. stopPropagation - prevents event traveling further up or down 3. stopImmediatePropagation - stopPropagation + prevents propagating event to other event listeners on same element return false to avoid event bubbling and prevent browser default actions, does work only in old style inline handlers but not with addEventListener method.

    ✅ All three verified. stopPropagation → own handlers 1 and 2 both run, the parent doesn't. stopImmediatePropagation → handler 1 only. return false → the parent still saw the event and defaultPrevented stayed false: ignored, exactly as you wrote.

    💡 They're independent: preventDefault stops the browser, stopPropagation stops the travel. ⚠️ stopPropagation inside a delegated handler is a trap — the event may never reach an ancestor that analytics or an outside-click handler depends on.

    5.5 ❓ Disabled buttons swallow clicks — you can settle this one

    Your note: clicks on any disabled element fires no click event at all, so nothing bubbles and attached handler won't triggered. If you need to detect clicks on disabled buttons then wrap them or have pointer-events: none in styling

    Click both. If the disabled one logs nothing while the wrapped one logs, your note is confirmed in this browser.

    ❓ This is the one claim jsdom would not confirm — it dispatched the click anyway. The HTML spec backs you up: a disabled form control must prevent queued click events from being dispatched. It applies to button, input, select, textarea, fieldset — not to a disabled-looking <div>.

    💡 For delegation: a disabled row button produces nothing for the parent to delegate, so "nothing happened" is the expected outcome, not a missing handler.

    5.6 e.target is whatever was under the cursor

    Click the row text and target is the <span>; click an icon and it's the <svg>. ✅ Verified in section 3: clicking row text logs target and currentTarget but never delete operation.

    const row = e.target.closest('li');
if (!row) return;                          // the guard that makes delegation safe
if (e.target.closest('.delete')) del(row.dataset.id);

    Never e.target === btn or e.target.classList.contains(...) — both break the moment there's a child element inside the button.

    5.7 Delegate to a container that outlives the rows

    The listener is on the <ul>; rows come and go. Re-render the container itself (innerHTML = …) and the listener dies with it — bind to a parent you never replace. 💡 document is the fallback but the loudest possible scope: every click in the page runs your handler. Prefer the nearest stable ancestor.

    5.8 Capture order beats registration order

    ✅ Verified in section 1: the capture listener was registered last and ran first. Same element, same phase → registration order decides.

    5.9 Delegation changes when a handler runs, not whether it can be slow

    One listener for 500 rows saves memory and setup, but it now runs for every click in the subtree. Keep it cheap: match, then hand off to a function. No layout reads (offsetHeight, getBoundingClientRect) inline.

    5.10 Nested retries of the DOM kind: two listeners, one intent

    A delegated parent handler plus a direct row handler both fire for the same click, in bubble order (row first, parent second). If both mutate state you get double deletes. Pick one layer — the same rule as retry layers in retry-with-backoff.js.

    6. Why this matters for React ⚛️

    Your note: React attaches one listener per each event type at root container element. The onClick in react code is not the actual DOM events but instead they were synthetic events tied to react synthetic tree. on click on any element react catches the native event at root and replays it through its synthetic tree. 1. synthetic events bubbling mechanism don't follow DOM tree instead it follow react synthetic tree. A modal using portal can be rendered at any other section in DOM tree but events still bubble up to the react parent that rendered it. will be a surprise on modal debugging. 2. stopPropagation: event.stopPropagation in react code stops the event bubbling for synthetic events but not for native event. native event would have already reached root, if any listeners were attached to parent via addEventListener method would still fire. 3. React onClick doesn't attach 500 listeners to 500 rows. Its a delegation under hood - do we need to do the delegation because we attach 500 listeners but not react already does it under hood

    💡 Answer to your question in (3): no. In React you don't hand-roll delegation for 500 rows — onClick per row is already delegated, and a per-row closure is the idiomatic, type-safe way to pass the row id. Hand-rolled delegation in React is for the rare case of a huge list where you also want to avoid 500 closures.

    ⚠️ One version detail worth naming: React 17+ attaches at the root container; React 16 attached at document. Mixing a React 16 app with your own document-level listener is where the ordering surprises came from.

    7. When NOT to use delegation ❌

    Your note: 1. single element with single handler - delegation adds indirection for nothing 2. event doesn't bubble and capture workaround is confusing with N listeners. 3. You need stopPropagation semantics between siblings, which delegation wont allow that.

    4. The container is re-rendered wholesale, so the listener keeps dying (section 5.7).

    8. Interview Q&A 🎤

    Q1. Walk me through what happens when I click a button.

    The browser computes the path window → … → target, runs capture listeners on the way down, then the target's, then bubble listeners on the way back up. addEventListener is bubble-phase unless you pass capture. (section 1)

    Q2. Order of logs for outer-capture, inner-bubble, target, outer-bubble?

    outer capture → button click → inner bubble → outer bubble — and the capture listener was registered last. (section 1, section 5.8)

    Q3. target vs currentTarget?

    target is what was hit and never changes during dispatch; currentTarget is the element whose listener is running, so it differs per handler. Valid only during dispatch. (section 2)

    Q4. What is delegation, and why does it work for rows added later?

    One listener on a stable ancestor. The event reaches the ancestor regardless, so nothing needs binding per row. Verified: a row created after bind still triggers it. (section 3)

    Q5. Why closest() instead of comparing e.target?

    The click may land on a span or an icon inside the button. closest() walks up from the target to the first match, and clicking dead space must produce no action. (section 5.6)

    Q6. preventDefault vs stopPropagation vs stopImmediatePropagation?

    Stop the browser's default action; stop travel through the tree; stop travel and the remaining listeners on the same element. (section 5.2)

    Q7. Does return false work?

    Only in old inline handlers. In an addEventListener callback it's ignored: the event still bubbled and defaultPrevented stayed false. (section 5.2)

    Q8. Which events don't bubble, and what do you do about it?

    focus, blur, mouseenter, mouseleave, element scroll. Use the bubbling twin, or listen in the capture phase. (section 5.3)

    Q9. Why didn't my delegated handler fire for a disabled button?

    A disabled form control dispatches no click at all, so there's nothing to delegate. (section 5.5)

    Q10. How do you remove many listeners cleanly?

    One AbortController: pass { signal } to each addEventListener and abort once. removeEventListener would need the identical function reference and capture flag. (section 4)

    Q11. React: I called stopPropagation in onClick — why did my document listener still run?

    React listens at the root container, so the native event already travelled there before your synthetic handler ran. Synthetic propagation follows the React tree, which is also why portals bubble to the React parent rather than the DOM parent. (section 6)
